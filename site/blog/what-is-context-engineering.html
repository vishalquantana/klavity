What Is Context Engineering? A Guide for Vibe Coders

Klavity7 min read
TL;DRContext engineering is the practice of controlling what an AI coding agent sees before it writes code - files, schemas, conventions, errors and test output. It has replaced prompt engineering as the main lever on code quality, because agents rarely fail from bad wording; they fail from missing interfaces and missing evidence. Every recurring class of AI-generated bug maps to a specific context gap.

Context engineering is the practice of deciding what an AI coding agent sees before it writes a line of code — which files, specs, type definitions, conventions, error messages and test results land in its working context. It has largely replaced prompt engineering as the main lever on output quality, because modern coding agents rarely fail from a badly worded instruction. They fail because they could not see the database schema, the helper function that already exists, or the console error your user actually hit. Good context engineering means the agent writes code against your real system. Bad context engineering means it writes plausible code against a system it imagined.

What is context engineering, exactly?

An AI coding agent has no memory of your project between runs. Its entire world is the context it is given at generation time: the system prompt or rules file, the files that are open or retrieved, documentation snippets, your conversation so far, and the output of any tools it ran. Everything it “knows” about your codebase arrives through that window, and anything missing from it gets filled in by statistical guesswork.

Context engineering treats that window as a build input you control, rather than something that just happens. Instead of rewording your request until the output improves, you change what the model can see. The same one-line request produces very different code depending on whether the agent can read your schema or has to invent one.

The three things context has to carry

  • Intent — what should happen, specific enough that someone could check it afterwards.
  • Interfaces — the real signatures, types, schema fields and route names the new code has to match.
  • Evidence — what actually happens today: the failing test, the stack trace, the reproduction steps.

Most bad AI output traces back to one of those three being absent. Prompts usually carry intent. They almost never carry interfaces or evidence unless you deliberately put them there.

How is context engineering different from prompt engineering?

Prompt engineering optimises the instruction. Context engineering optimises the information surrounding it. They are complementary, but they fail in different ways and the fixes are not interchangeable.

If rewording a prompt three times has not helped, the problem is almost always missing context, not missing adjectives.

Why does context engineering decide how many bugs your AI writes?

There are a handful of recurring bug patterns in AI-generated code, and each one maps to a specific gap in context:

  • Hallucinated interfaces. When the real function signature or column name is not in context, the model supplies the most statistically likely one. The result looks correct and fails at runtime — the pattern behind most AI-generated code bugs.
  • Duplicate implementations. An agent that cannot see your existing formatDate helper writes a second, slightly different one. Nothing breaks immediately; the two drift apart later.
  • Deprecated patterns. Model training data has a cutoff. Without current documentation pinned into context, agents reach for the library API they saw most during training, which may no longer be the recommended one.
  • Diluted constraints. Long, rambling context buries the one rule that mattered. Information at the very start and very end of a context window is retrieved more reliably than material in the middle, so a critical constraint parked mid-conversation is the easiest thing for an agent to lose.
  • Missing failure paths. A prompt that describes only the happy path yields code that only handles the happy path — no empty states, no timeouts, no error branches. That gap is why testing AI-generated code catches so much on first run.

What belongs in an AI coding agent's context?

Context sourceWhat it prevents
Rules file (CLAUDE.md, AGENTS.md, .cursorrules)Convention drift, wrong stack choices, edits to files that should not be touched
Type definitions and database schemaInvented fields, wrong nullability, mismatched enums
The existing module the change touchesDuplicate logic and contradictory implementations
Current library or API documentationDeprecated calls from stale training data
Failing test or type-check output, verbatimFixes that address a misremembered version of the error
A reproducible bug report: steps, console, network, environment“Cannot reproduce” loops and fixes to the wrong layer
Acceptance criteria for the taskScope creep and work nobody can verify

Note what is not on that list: your entire repository. Dumping everything in is not context engineering, it is the diluted-constraint failure above. The goal is a small, high-signal set.

How do you do context engineering in Cursor, Claude Code, or Lovable?

  1. Write a short rules file. Stack, versions, directory conventions, the two or three things never to change. Keep it tight — a rules file long enough to compete with the task itself stops functioning as a rule.
  2. Reference files explicitly. Name the files the change touches instead of trusting automatic retrieval to find them. In chat-only builders such as Lovable, Bolt or v0, paste the schema and the exact error text directly into the message.
  3. Give the contract before the implementation. Supply the type, schema or API signature first, then ask for the code that satisfies it. This is the cheapest single intervention available, and it is most of what spec-driven development formalises.
  4. Keep one task per context. Start a fresh thread for unrelated work so abandoned decisions from the last task do not leak into the next one.
  5. Close the loop with real tool output. Let the agent read the test run, the type-check or the console trace rather than describing it secondhand. A pasted stack trace beats a paraphrase every time.

Where does QA fit into context engineering?

QA produces the evidence half of context, and it is the half almost everyone skips. A failing assertion, a console error with a stack trace, a screenshot and the exact steps that caused it are the highest-value tokens you can hand an agent. Without them you are asking it to guess what went wrong; with them you are asking it to fix a specified defect. This is the same loop described in the complete guide to AI QA.

What does a context engineering checklist look like?

  • Is there a rules file, and is it short enough that an agent will actually respect it?
  • Does the agent have the real schema and types, not a description of them?
  • Did you name the existing files this change touches?
  • Are version-sensitive library docs pinned, or is the model guessing from training data?
  • Is the task scoped to one change in a clean context?
  • Can the agent read test and console output itself?
  • When a bug appears, does it get reproduction steps and logs — or a sentence of prose?

Context engineering is not a prompt trick; it is supply-chain hygiene for the inputs your AI builds from. Pair it with a verification step and the two reinforce each other: better context produces fewer bugs, and the bugs you do catch become the context that prevents the next batch.

FAQ

What is context engineering in simple terms?

It is choosing what information an AI coding agent can see before it generates code. That includes your rules file, type definitions and schema, the existing files the change touches, current library docs, and real error or test output. Anything missing from that context gets filled in by guesswork.

Is context engineering the same as prompt engineering?

No. Prompt engineering changes the wording of the request and fixes output that is in the wrong shape. Context engineering changes what information surrounds the request and fixes code that is confidently wrong about your system. If rewording a prompt repeatedly has not helped, the gap is context, not phrasing.

Why does context engineering reduce bugs in AI-generated code?

Because the common bug patterns each trace to a context gap: hallucinated function signatures when the real interface is absent, duplicate helpers when existing code is not visible, deprecated API calls when current docs are not pinned, and missing error handling when only the happy path was described.

Should I just put my whole codebase in context?

No. Oversized context dilutes the constraints that matter, and material in the middle of a long context window is retrieved less reliably than material at the start or end. Aim for a small, high-signal set: the rules file, the relevant interfaces, the files being changed, and the actual error output.
