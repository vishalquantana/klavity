What Is Agentic Coding? A Definition and QA Playbook

Klavity7 min read
TL;DRAgentic coding is development where an AI agent takes a goal and executes it itself — reading files, editing several of them, running commands and iterating until its own checks pass. Unlike autocomplete, you review the change after it is applied, not before. The verification that used to come free with typing the code yourself has to be put back deliberately, against the running product.

Agentic coding is software development where you give an AI coding agent a goal rather than a line of code, and it plans and carries out the work itself — reading files, editing several of them, running commands, inspecting the result and iterating until it decides the task is done. Cursor's agent mode, Claude Code, Replit Agent and Copilot's agent features all work this way. The practical difference from older AI assistance is scope and timing: autocomplete offers one line that you read before accepting, while an agent hands you a finished multi-file change that you review afterwards, if at all.

What is agentic coding, exactly?

Agentic coding describes a loop rather than a feature. You state an outcome — "add Google sign-in", "make the dashboard load faster", "fix the failing checkout test" — and the agent runs a cycle: plan the steps, edit code, execute something (a build, a test, a script), read what came back, then correct itself and continue. It stops when its own checks pass or when it runs out of ideas.

Three properties separate it from a chat window that returns a snippet:

  • Autonomy over steps. You approve the destination, not each turn. The agent chooses which files to open and what order to do things in, and those choices are not in the final diff.
  • Multi-file scope. A single instruction can touch a component, a route, a migration, a config file and a test. Nothing warns you when it edits a file you never mentioned.
  • Tool use. The agent runs your terminal, your package manager, your test suite — sometimes your database. It is acting on your project, not just writing text about it.

That third property is why agentic coding is genuinely more productive than autocomplete, and also why it needs a different kind of verification. An agent that can run commands can also make its own work look finished.

How is agentic coding different from vibe coding and autocomplete?

These terms get used interchangeably and shouldn't be. They differ in how much you read before the code is yours.

ModeYou provideYou get backWhat you typically readMain QA risk

Vibe codingA description of the appWorking-looking featuresLittle or none — you judge by the running resultNo idea which paths were never exercised

Agentic coding and vibe coding overlap in practice — many non-technical founders are doing both at once — but they fail differently. Vibe coding leaves you unsure what the code does. Agentic coding leaves you unsure what the code changed.

Why does agentic coding break the assumptions QA is built on?

Most QA habits assume a human wrote the change, so the change is roughly the size of what a human can hold in their head. Agents break that assumption in three specific ways.

Review happens after the work, at a size attention can't match. A prompt that takes seconds to write can produce a diff that takes a long, careful sitting to read properly. The realistic options are to skim or to become the bottleneck, and skimming a diff is how changes outside the stated scope get merged without anyone noticing them.

The agent is often its own only verifier. When the same model writes the feature and the test for the feature, both inherit the same misunderstanding of the requirement. The suite goes green because the test encodes what the code does, not what you asked for. Green tests written by the author of the bug are not evidence.

Correctness of code is not correctness of product. An agent can be right about every function it wrote and still break the app, because it did not know that one of the files it refactored was also used by your billing webhook. Static review catches malformed code; it does not catch a flow that no longer completes. That gap is the core argument of our complete guide to AI QA: verification has to happen against the running product, not just the diff.

What kinds of bugs does agentic coding produce?

The failure patterns are consistent enough to check for deliberately:

  • Invented interfaces. Calls to a library method, option or response field that is plausible but does not exist in the version you have installed. Common when the agent is working from a familiar pattern rather than your lockfile.
  • Swallowed errors. A try/catch added to make a build pass, which now hides the real failure at runtime. Nothing breaks; nothing works either.
  • Happy-path-only UI. The screen renders, the button exists, and the loading, empty, error and unauthorised states were never considered because nobody asked for them.
  • Missing authorisation on new paths. New endpoints and new routes are where permission checks go absent, because the agent was focused on making the feature work, and it worked — as the logged-in developer.
  • Drifted duplicates. The same logic generated in two places across two sessions. Fixing one copy leaves the other live.
  • Collateral edits. A tidy-up of an import, a renamed prop, a "while I was here" change in a file you never put in scope.

How do you QA an agentically coded app?

The goal is not to review more. It is to move verification somewhere a human can realistically do it — the behaviour of the running app — and to keep each agent task small enough to judge.

  1. Constrain the blast radius before you run the agent. One task per run, with a stated scope, and a commit between tasks. A 60-line diff you actually read beats a 600-line diff you skim.
  2. Review by behaviour, not by file. Ask what a user can now do that they couldn't, and what they could do before that might have moved. Then check the files the agent touched that you didn't expect — that list is where the surprises live. Our notes on reviewing AI-generated code go through this in order.
  3. Verify from outside the code. Click the flow end to end, logged out as well as logged in. Sims does this as AI personas that use the product the way different real users would, so the states the agent skipped get exercised by someone other than the agent.
  4. Don't let the agent be your only test author. Write — or have something independent write — the assertions for the requirement, not for the implementation.
  5. Lock the flows you cannot afford to lose. Signup, login, checkout, save. AutoSim keeps those E2E tests passing through the selector churn that agent refactors cause, which is usually why handwritten suites get abandoned.
  6. Make real-world capture one click. When a client or a user does hit something, Snap turns a right-click into a report with the console, network and environment attached, so the next agent prompt starts from evidence instead of "it's broken".

What should you check before shipping an agent's work?

A short pass that catches most of the above, in the order that finds problems fastest:

  • Did any file change that wasn't in the scope you gave? Read those first.
  • Does every new network call have a visible failure state in the UI?
  • Is there a permission check on every new endpoint or route?
  • Does the main flow still complete for a brand-new, logged-out visitor?
  • Do the new tests assert the requirement, or just restate the code?

Agentic coding is a real change in how much software one person can ship, and it is not going back. What it removes is the incidental verification that used to come free with typing the code yourself. That has to be put back deliberately — and it has to live where the product runs, not only where the diff is read.

Key takeaways

  • Give the agent one scoped task per run and commit between tasks, so each diff stays readable.
  • Read the diff by behaviour, and read the unexpected files first.
  • Never let the agent be the only author of the tests that verify its own work.
  • Verify against the running product — logged out as well as logged in — not just the code.

FAQ

What is agentic coding in simple terms?

It is coding where you give an AI agent an outcome — 'add Google sign-in', 'fix this failing test' — and the agent decides the steps: which files to open, what to edit, what commands to run. It keeps iterating until its own checks pass, then hands you a finished multi-file change to review.

Is agentic coding the same as vibe coding?

They overlap but fail differently. Vibe coding means judging the app by the running result rather than the code, so you are unsure what the code does. Agentic coding means an agent applies multi-file changes to a real repo, so the harder question is what the change touched beyond what you asked for.

Do I still need to review the code if the agent's tests pass?

Yes. When the same model writes the feature and its tests, both carry the same misunderstanding of the requirement, so the suite can go green while the behaviour is wrong. Tests written by the author of the bug are not independent evidence — verify the requirement against the running product.

What is the fastest way to QA an agent's change?

Start with the files that changed but were not in the scope you gave; that is where collateral edits hide. Then run the main flow end to end both logged in and logged out, and check that every new network call has a visible failure state in the UI.
