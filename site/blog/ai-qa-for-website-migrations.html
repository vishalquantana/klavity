AI QA for Website Migrations: A Pre-Launch Playbook

Klavity7 min read
TL;DRAI QA for website migrations works by comparison, not inspection: crawl the live old site first to capture every URL, screenshot and flow, then replay that baseline against staging. The bugs that sink migrations are absences — a form that renders but never delivers, a ranking page that quietly 404s — and they are invisible to any test that only looks at the new build.

AI QA for website migrations means using automated agents to capture a verified baseline of the old site, then replay that same baseline against the new one — so every URL, form, redirect and layout is checked before launch instead of after a client reports it. On a migration the risk is not that the new site is broken; it is that something that used to work quietly stopped working. AI QA closes that gap by testing the old and new builds as a pair rather than testing the new build on its own.

Why do website migrations break things nobody noticed in QA?

A migration changes the substrate under thousands of small behaviours at once: URL structure, templating, CSS cascade, form handlers, analytics hooks, redirects, image paths, CMS field mappings. Most of those are never written down anywhere. The old site is its own spec, and nobody ever read the whole thing.

That is why migration bugs have a signature shape:

  • They are absences, not errors. A contact form that silently stops emailing throws no exception and lights up no dashboard. Error monitoring only sees what crashes.
  • They live on pages nobody clicks during QA. Teams test the homepage, the pricing page and one blog post. The broken page is a 2019 case study that still ranks and still converts.
  • They surface on real devices and real data. A layout that holds with lorem ipsum collapses on a 94-character German product name.
  • They are found by the client. Which is the one failure mode an agency cannot afford, because it reframes the whole project as "the rebuild broke our site".

Manual QA fails here not from laziness but from arithmetic. A 400-page site has far more states than any human can click through in the two days between staging freeze and launch — and it needs re-checking after every fix.

What does AI QA for website migrations actually check?

Four passes, run against both builds and compared. Each one maps to a class of migration failure:

PassWhat it comparesMigration bug it catches
URL & redirect parityEvery old URL → status code on new hostDead links, 404s on ranking pages, redirect chains and loops
Content parityHeadings, body text, images, metadata per pageTruncated CMS fields, missing images, lost meta descriptions, empty templates
Visual diffScreenshots at multiple widths, old vs newBroken responsive breakpoints, overflow, webfont fallbacks, z-index regressions
Flow replayReal journeys: search → form → submit → confirmForms that render but never deliver; broken checkout, login, booking

The important word is parity. A generic test suite asks "does this page work?" A migration suite asks "does this page still do what the old one did?" — a much sharper question, and one you can only ask if you crawled the old site before switching DNS.

How do you set up migration QA before you cut over?

The sequence matters more than the tooling. Doing step 1 after cutover is the single most common and most expensive mistake on a migration, because once the old site is gone the baseline is unrecoverable.

  1. Crawl the live old site first. Export every URL with status code, title, H1 and a screenshot at desktop and mobile widths. Keep it in the repo, not someone's laptop. This is your spec.
  2. Rank URLs by consequence, not by depth. Pull the top pages from analytics and Search Console, add every page with a form or a payment step, and add every page a client has ever personally mentioned. Those get full flow testing; the long tail gets parity checks.
  3. Write down the flows the site actually earns money with. Usually three to six: contact, quote request, booking, signup, checkout, search. Everything else is secondary.
  4. Replay the baseline against staging and fix in loops. The first run is noisy — expect intentional redesign differences. Triage once, mark the accepted diffs, then re-run so later runs show only real regressions.
  5. Keep the suite running after launch. Migration bugs arrive late: cached pages expire, cron jobs fire weekly, a CDN rule propagates on day three.

Does this apply to vibe-coded rebuilds too?

It applies more. A common 2026 pattern is rebuilding an aging site in Cursor, Lovable, v0 or Bolt in a few days. The output ships fast and looks right, which is precisely the risk: generated code tends to reproduce the appearance of the old site without its behaviour. Forms get the markup but not the handler. Pages get the layout but not the redirect. Nothing errors; things just quietly do less.

If you rebuilt with AI, the baseline crawl is non-negotiable, and so is flow replay on anything that submits data. The model never saw your old backend. It cannot know what the form used to do.

What should you check in the first 48 hours after cutover?

Launch is not the end of migration QA — it is where a different set of failures starts. Watch these specifically:

  • Redirects under real traffic. Crawl your top URLs again from outside your network, after DNS and CDN caches settle.
  • Form deliverability end to end. Submit a real test entry and confirm it arrived in the inbox or CRM — not just that the thank-you page rendered.
  • Analytics and conversion tracking. Migrations routinely drop tags, which hides every other problem by making traffic look merely "down".
  • Scheduled and transactional email. Weekly digests and receipts break on a schedule you will not notice for days.
  • Search Console coverage. New 404s and soft-404s appear within days and are the clearest early signal that a parity check was missed.

Key takeaways

  • Crawl and screenshot the live old site before cutover — that export is your spec.
  • Rank URLs by traffic and revenue, not by site depth, then flow-test the top set.
  • Verify forms end to end: confirm delivery to inbox or CRM, not just the thank-you page.
  • Keep the suite running for 48 hours past launch — cache, cron and CDN bugs arrive late.

FAQ

When should migration QA start?

Before cutover, while the old site is still live. The baseline crawl — every URL with its status code, title and screenshots at desktop and mobile widths — can only be captured from the old build. Once DNS has switched, that reference is gone and you are left guessing at what used to work.

What is the most commonly missed migration bug?

Forms that render correctly but no longer deliver. The markup and the thank-you page survive the migration while the handler, SMTP credentials or CRM integration does not. Nothing errors, so error monitoring stays silent. The only reliable check is submitting a real entry and confirming it arrived.

Do I still need migration QA if a developer rebuilt the site by hand?

Yes. Migration regressions come from the thousands of undocumented behaviours in the old site, not from developer skill. No one has read the whole old site, so no one can hold its full behaviour in their head — which is exactly why a captured baseline beats a careful reviewer.

How is this different from running a normal test suite on the new site?

A normal suite asks whether the new site works. Migration QA asks whether it still does what the old one did. Those differ on every page where the old behaviour was never specified — which, on most legacy sites, is nearly all of them.
