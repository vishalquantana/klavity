ChatGPT App Testing: A QA Guide for Pasted-In Code

Klavity7 min read
TL;DRChatGPT app testing is different from reviewing a teammate's code: the model never saw your schema, middleware or lockfile, so defects concentrate at the seams rather than inside the snippet. Test execution, imports, server-side authorization and error states first — and re-run the pass after every regeneration, because re-prompting produces new code, not a patch.

ChatGPT app testing means verifying code that was written without any view of your repository — so you test the seams first, not the logic inside the snippet. Execute every path the pasted code touches, check its imports and config keys against what is actually installed, then verify server-side authorization and error states. Those passes catch most of what ChatGPT gets wrong once its output lands in a real project.

This is a different job from reviewing code a teammate wrote. A teammate has seen your schema. ChatGPT has seen your prompt.

Why is ChatGPT app testing different from testing code you wrote?

Three structural facts about how the code arrives decide where you should spend testing effort.

It has no repository context unless you pasted it. ChatGPT does not see your file tree, your database schema, your auth middleware, your routing conventions or your lockfile. It infers them from the shape of your prompt. That means the generated function body is often fine in isolation, while the join between that function and your project — the import path, the environment variable name, the table or column it selects, the middleware it forgets to wrap — is where defects concentrate.

It cannot run what it produces. There is no compile step, no failing test and no stack trace feeding back into the answer. Code you write gets corrected by the runtime within seconds; code from a chat window is syntactically confident and behaviorally unverified until you execute it yourself. Your first test is therefore not unit-level correctness. It is: does this path execute at all, end to end, with real data?

Regeneration is not idempotent. Ask the same question twice and you get different code. So when you fix a bug by re-prompting, you have not patched the thing you tested — you have replaced it with something new that needs the same pass again. Teams that treat a regenerated block as "the same code, fixed" are the ones who ship the same bug twice.

Where does ChatGPT-generated code usually break?

The failure modes repeat, which is good news: a short checklist covers most of them.

Imports or packages that don't exist, or belong to another major versionTrained across mixed library vintages; it cannot read your lockfileResolve every new import against the installed version before testing behavior
Authorization checked in the UI onlyThe prompt described a screen, so it secured a screenCall the endpoint directly with a non-owner session
Happy path only — no empty, loading or failure stateNothing in the prompt described failureRun the flow with no data, a dropped network and an expired session
Wrong field or table names that still compilePlausible naming invented in place of your real schemaAssert against a real record, not a mock
Duplicated logic that drifts from the originalEach answer is generated fresh, with no memory of the earlier copySearch for the same rule implemented twice, then delete one

Two of these deserve a flag. Invented references are common enough to have a name — see AI code hallucinations for how to catch phantom APIs, packages and config keys before launch. And missing server-side authorization is the one defect on this list where the blast radius is other people's data, not a broken screen, which is why it belongs at the top of every pass.

What should you test first in a ChatGPT-built app?

Order by what a failure would cost you, not by what is easy to test. A useful sequence:

  1. Authentication and data access. Can a logged-out visitor reach anything? Can one user read or modify another user's records by changing an ID?
  2. Anything that writes or deletes. Create, update, delete, bulk actions, imports. Destructive paths are rarely what the prompt focused on.
  3. Money and third parties. Checkout, webhooks, email sends, external APIs. Verify the failure branch, not just the success one.
  4. Forms and validation. Submit empty, submit twice, submit the wrong type, submit a very long string.
  5. Error and empty states. New account with zero data, failed request, expired session, slow connection.
  6. Mobile and a second browser. Generated layouts are usually tested, if at all, in one window at one width.
  7. Cosmetic polish. Last. It is also the only category your client will notice unprompted, which is why it cannot be first.

How do you run ChatGPT app testing with no test suite at all?

Most ChatGPT-built apps have no tests, and the instinct — write unit tests for the generated code — is usually wrong at this stage. Generated code churns: you will re-prompt that function three more times this week, and the unit tests go stale with it.

Test at the seams instead:

  • Use your prompt as the spec. What you asked for is the acceptance criteria. Walk the feature as a user and check it against the prompt, line by line. Anything the prompt did not mention is untested by definition.
  • Cover a handful of end-to-end paths over the flows that would embarrass you in front of a client — sign up, log in, the core action, pay. End-to-end tests survive regeneration because they assert on behavior, not on the internals that keep changing.
  • Turn every bug you find into a test. A bug that shipped once will ship again the next time you regenerate nearby code. This is the only test suite that compounds while the code underneath you is still moving.
  • Re-run the pass after each regeneration. Cheap if the paths are automated; otherwise it is the step everyone skips, and the reason "I already fixed that" turns into a client email.

Key takeaways

  • Test the seams first: imports, config keys, schema names, auth wrappers.
  • Call endpoints directly with a non-owner session before testing any UI.
  • Cover end-to-end paths, not unit tests, while generated code still churns.

FAQ

What should I test first in an app built with ChatGPT?

Authorization and data access. Generated CRUD code frequently enforces permissions in the UI only, so call the endpoint directly with a non-owner session before you test anything cosmetic. Then test anything that writes or deletes, then payments and third-party calls, then forms, then error and empty states.

Should I write unit tests for ChatGPT-generated code?

Not as the first move. Generated code churns — you will likely regenerate the same function several times — so unit tests on its internals go stale fast. Cover a few end-to-end paths over the flows that matter, and add a regression test each time you find a real bug.

Why does ChatGPT code break when it looked correct in the chat?

Because the model could not run it and could not see your project. Imports may target a different library version than the one installed, config keys and schema names are plausible guesses, and failure paths are usually absent because nothing in the prompt described failure.

Do I need to re-test after re-prompting a fix?

Yes. Generation is not idempotent — the same prompt returns different code. A re-prompted fix is new code rather than a patch to the version you already verified, so the pass has to run again.
